# Python 패션디자인 퀴즈 게임

대전코디세이 2차 Python 미션의 터미널 기반 퀴즈 게임입니다.
필수 기능과 선택 보너스 5개를 구현했으며 Python 표준 라이브러리만 사용합니다.
`Quiz`는 문제 하나를, `QuizGame`은 메뉴·게임 진행·저장·기록을 담당합니다.

## 퀴즈 주제와 선정 이유

**패션디자인 기초 지식**을 주제로 실루엣, 다트, 면 섬유, 시접, 균형 등
의복 디자인과 제작의 기본 개념을 복습합니다. 기본 문제 5개를 제공하며
사용자가 문제·선택지·정답·힌트를 추가할 수 있습니다.

## 기능 목록

| 메뉴 | 기능 |
|---|---|
| 1. 퀴즈 풀기 | 풀 문제 수 선택 → 중복 없는 랜덤 출제 → 정오답·최종 결과 |
| 2. 퀴즈 추가 | 문제·선택지 4개·정답 번호 1~4·선택적 힌트 등록 및 저장 |
| 3. 퀴즈 목록 | 등록된 모든 문제 제목·개수 확인 |
| 4. 점수 확인 | 완료한 게임의 최고 점수 확인 |
| 5. 종료 | 저장 후 종료. 기존 종료 번호 유지 |
| 6. 퀴즈 삭제 | 목록 번호 선택 → 삭제 확인 → 파일 반영 |
| 7. 점수 기록 | 완료한 회차의 날짜·시간·문제 수·정답 수·힌트 수·점수 조회 |

숫자 입력은 앞뒤 공백을 제거합니다. 문자·빈 입력·허용 범위 밖 입력은 안내 후 다시 받습니다.
문제와 선택지는 빈 문자열을 허용하지 않으며, 등록 시 힌트는 Enter로 생략할 수 있습니다.
빈 퀴즈 목록과 아직 게임을 완료하지 않은 상태도 안내합니다.
Ctrl+C와 EOF는 안내 후 가능한 범위에서 저장하고 종료합니다.
등록·삭제 확인 중 입력을 중단하면 미완성 등록이나 미확인 삭제를 반영하지 않습니다.
풀이 도중 중단한 회차는 점수 기록과 최고 점수에 반영하지 않습니다.

## 보너스 5개 사용법

### 1. 랜덤 출제

등록된 문제에서 `random.sample`로 중복 없이 무작위 선택·배열합니다.
문제 수를 전체 개수로 선택해도 출제 순서를 무작위로 정합니다.
매번 순서가 반드시 다르다는 뜻은 아니며 우연히 같은 순서가 나올 수 있습니다.
원본 문제 목록 순서와 선택지 번호는 바꾸지 않습니다.

### 2. 풀 문제 수 선택

메뉴 `1`에서 `풀 문제 수`를 입력합니다. 등록 개수가 6개라면 1~6 중 선택합니다.
0·초과 개수·문자·빈 입력은 다시 입력받습니다.

### 3. 힌트와 감점

풀이 중 정답 대신 `0`을 입력하면 힌트를 표시합니다.
등록된 힌트가 없으면 오답 선택지 두 개를 제외하는 안내를 제공합니다.
따라서 이전 버전에서 추가한 문제도 힌트를 사용할 수 있습니다.

- 기본 점수: `round(정답 수 / 푼 문제 수 * 100)`
- 최종 점수: `max(0, 기본 점수 - 힌트를 사용한 문제 수 * 10)`
- 같은 문제에서 0을 반복 입력해도 감점은 한 번뿐입니다.
- 예: 2문제 모두 정답 + 한 문제에서 힌트 사용 = 90점.
- 최고 점수와 기록에는 감점 후 최종 점수를 반영합니다.
- 점수는 0점 아래로 내려가지 않습니다.

### 4. 퀴즈 삭제

메뉴 `6`에서 목록의 문제 번호를 선택합니다. `0`은 취소입니다.
대상을 확인한 뒤 `1`을 입력해야 삭제하며 `2`는 취소입니다.
삭제 후 즉시 저장합니다. 마지막 문제도 삭제할 수 있으며 빈 목록을 정상 처리합니다.
과거 점수 기록과 최고 점수는 문제 삭제 후에도 유지합니다.

### 5. 점수 기록 히스토리

메뉴 `7`에서 완료한 게임을 최신순으로 확인합니다.
한국 시간(UTC+09:00) 날짜·시간, 푼 문제 수, 정답 수, 힌트 수, 최종 점수를 저장합니다.
기존 최고 점수가 있어도 이전 버전의 회차 기록을 만들어내지는 않습니다.
확장 버전에서 완료한 회차부터 실제 기록이 쌓입니다.

## state.json 설명

현재 터미널 위치와 관계없이 프로젝트 루트(`game.py`와 같은 폴더)에 UTF-8로 저장합니다.
추가·삭제·게임 완료·종료 시 저장하며 재실행하면 불러옵니다.
아래는 필드 구조 예시이며 `quizzes`에는 실제 등록된 모든 문제가 들어갑니다.

```json
{
  "quizzes": [
    {
      "question": "의복의 전체적인 외곽선이나 윤곽을 뜻하는 용어는?",
      "choices": ["실루엣", "다트", "시접", "안감"],
      "answer": 1,
      "hint": "의복의 전체적인 형태를 떠올려 보세요."
    }
  ],
  "best_score": 90,
  "history": [
    {
      "played_at": "2026-11-16T00:00:00+09:00",
      "total": 1,
      "correct": 1,
      "hints_used": 1,
      "score": 90
    }
  ]
}
```

- `quizzes`: 문제 목록. 각 문제의 정답은 1~4 정수이고 선택지는 4개입니다.
- `hint`: 선택적 문자열. 이전 파일에 없으면 빈 문자열로 읽고 오답 두 개 제외 힌트를 제공합니다.
- `best_score`: 미플레이는 `null`, 완료한 적이 있으면 0~100 정수입니다. 완료한 0점과 구분합니다.
- `history`: 완료한 회차 목록. 예전 파일에 없으면 빈 목록으로 읽습니다.
- **이전 저장 파일의 추가 문제와 최고 점수를 유지합니다.** 첫 정상 저장 시 새 필드를 추가합니다.
- 파일이 없으면 기본 문제로 시작합니다. JSON·스키마·UTF-8 손상은 안내 후 기본 데이터로 복구합니다.
- 손상 파일은 다음 정상 저장 시 기본 데이터로 교체됩니다. 실행 중 자동 백업은 하지 않습니다.
- 읽기 오류는 기본값으로 시작하고, 쓰기 오류는 저장 실패를 안내합니다.
- 저장 실패 시 메모리 변경은 남지만 재실행 시 유지되지 않을 수 있습니다.
- 같은 폴더의 임시 파일을 완성한 뒤 교체해 저장 중 원본 손상 가능성을 줄입니다.
- `state.json`은 사용자 데이터이므로 Git에 포함하지 않습니다.

## 설계 선택 이유와 저장 방식의 한계

### 클래스와 함수의 선택 기준

`Quiz`는 같은 구조의 문제·선택지·정답·힌트를 한 객체에 묶고 생성자에서 검증합니다.
`QuizGame`은 목록·최고점·기록과 이를 변경하는 동작을 함께 관리합니다.
그래서 함수마다 상태를 반복 전달하거나 전역 변수로 흩어 두는 일을 줄이고,
게임별 상태와 임시 저장 경로를 분리해 테스트할 수 있습니다.
반대로 클래스는 `self`·생성자·객체 변환을 알아야 하고 메서드의 실행 순서가 상태에 영향을 줍니다.
작은 함수·딕셔너리 기반 프로그램은 더 단순할 수 있어, 상태가 없는 입력 검증은 함수로 유지했습니다.

`Quiz.display/check_answer/show_hint`는 한 문제의 동작이고,
`QuizGame.play/add_quiz/delete_quiz`는 게임 진행과 목록 변경,
`load_state/save_state`는 파일 I/O를 맡습니다. `input_helpers`는 터미널 입력만 검사합니다.
입력은 공백 제거 → 정수 변환 → 범위 검사 순서이며,
정답 비교는 `type(answer) is int`로 `True`가 숫자 1처럼 처리되는 것을 방지합니다.

### JSON을 선택한 이유

JSON은 사람이 읽을 수 있는 구조화된 텍스트이고, 선택지 배열·문제 객체·회차 기록을
한 파일에 담을 수 있습니다. 표준 `json` 모듈과 UTF-8을 사용해 외부 패키지 없이
Windows와 WSL에서 한글 데이터를 읽고 씁니다.
단, JSON은 데이터 형식이므로 클래스 객체를 직접 저장하지 않고 dict/list로 변환해야 하며
정답 범위나 필드 구조 같은 스키마 검증은 코드가 담당합니다.
CSV보다 중첩 목록을 표현하기 쉽고, 작은 단일 사용자 프로그램에서는 데이터베이스보다 구성이 단순합니다.

`quizzes`의 한 객체에 문제·선택지·정답·힌트를 묶어 관계를 유지하고,
`history`의 한 객체에는 한 회차의 날짜·문제 수·정답 수·힌트 수·점수를 묶습니다.
과거 집계값은 현재 문제를 삭제해도 유지됩니다. 최고점은 별도로 두어 옛 파일의 점수도 보존합니다.

### 성능·메모리·동시 접근의 한계

현재는 파일 전체를 읽고 매 저장마다 전체 JSON을 다시 씁니다.
전체 데이터 크기를 S라고 하면 I/O·파싱·직렬화 비용은 대체로 S에 비례하며,
문제와 제한 없이 쌓이는 history가 커질수록 대기 시간과 메모리 사용이 증가합니다.
메모리에는 전체 문제·기록뿐 아니라 로드·저장 변환용 dict/list도 잠시 공존하고,
디스크에는 기존 파일과 임시 파일을 함께 둘 공간이 필요합니다. 대용량 성능을 측정하거나 보장하지는 않았습니다.

파일 잠금·트랜잭션·버전 검사가 없어 두 프로세스가 동시에 실행되면 나중 저장이
앞선 변경을 덮어쓸 수 있습니다. 임시 파일 후 교체는 중간에 잘린 파일의 위험을 줄이지만
동시 변경을 병합하거나 전원 장애 내구성까지 보장하지 않습니다.
현재 전제는 작은 데이터·단일 사용자·한 번에 한 프로세스입니다.
규모가 커지면 기록 분리·페이지 조회를, 동시 사용이 필요하면 SQLite 같은 저장소를 검토합니다.

메서드별 책임, 스키마 이유, 오류별 복구, 수동 백업과 변경·테스트 대응은
[클래스와 JSON 저장 설계](docs/design.md)에 정리했습니다.

## 저장 시점·로드 순서·중단 정책

로드는 기본값 준비 → 프로젝트 루트 `state.json` 읽기 → JSON·필드·개별 문제·기록 검증
→ 모두 유효할 때 적용 순서입니다. 파일 없음·손상·읽기 실패는 안내 후 기본 데이터로 시작합니다.
검증 실패 시 정상 항목만 부분 복구하지 않으며, 다음 정상 저장 때 손상 파일을 교체합니다.

| 동작 | 저장 시점·내용 |
|---|---|
| 추가 | 힌트까지 모든 입력을 끝낸 뒤 문제 추가 및 즉시 저장 |
| 삭제 | 대상 선택·삭제 확인 후 목록 변경 및 즉시 저장 |
| 게임 완료 | 완료 회차의 최종 점수·기록·최고점을 함께 저장 |
| 메뉴 5 종료 | 현재 전체 상태 저장 시도 |
| Ctrl+C·EOF | 안내 후 종료 경로에서 저장 시도. 미완성 문제·확인 전 삭제·미완료 회차는 반영하지 않음 |
| 조회 | 조회 자체는 저장하지 않으며 이후 종료 시 저장 |

쓰기 실패 시 메모리 변경은 남고 다음 저장 동작에서 다시 시도하지만 자동 재시도 루프는 없습니다.
종료까지 실패하면 이번 변경이 유실될 수 있습니다.
자동 백업·restore 기능은 없으며, 게임 종료 후 정상 `state.json`을 수동 복사해 보관하고
백업의 문법·필드를 확인한 뒤 복구할 수 있습니다. [예외별 동작과 수동 복구](docs/design.md)를 참고하세요.

## 메뉴별 입력·출력 예시

아래는 사용법 예시이며 새로운 실행 로그를 꾸며 낸 것이 아닙니다.
무작위 문제와 점수는 실제 상태에 따라 달라집니다. 실제 대화 출력은 [bonus-demo.txt](docs/bonus-demo.txt)에 있습니다.

| 메뉴 | 입력 예 | 출력·결과 예 |
|---|---|---|
| 1 | `1` → 문제 수 `2` → 힌트 `0` → 각 문제 정답 | 두 문제 정답·힌트 1회면 최종 90점 |
| 2 | `2` → 문제·선택지 4개·정답 `1`·힌트 | `퀴즈가 추가되고 저장되었습니다.` |
| 3 | `3` | `등록된 퀴즈 목록 (총 6개)` 등 현재 개수와 문제 제목 |
| 4 | `4` | `최고 점수: 100점 (100점 만점)` 또는 미플레이 안내 |
| 5 | `5` | 저장 시도 후 `게임을 종료합니다.` |
| 6 | `6` → 대상 번호 → 확인 `1` | `퀴즈를 삭제하고 저장했습니다.`. 대상 `0` 또는 확인 `2`는 취소 |
| 7 | `7` | 날짜·시차·문제 수·정답 수·힌트 수·점수, 또는 기록 없음 안내 |

## 기본 문제 변경·확장 절차

`defaults.py`의 `default_quizzes()`는 `Quiz` 객체 5개를 반환합니다.
`Quiz("문제", ["선택1", "선택2", "선택3", "선택4"], 정답번호, "힌트")` 형식으로 편집·추가합니다.
정답은 1~4 정수이고 문제·선택지는 비어 있으면 안 됩니다. 힌트는 생략할 수 있습니다.
기존 정상 `state.json`이 있으면 그 데이터가 우선이므로 기본 문제 수정이 기존 파일에 자동 합쳐지지 않습니다.
현재 사용자에게 문제를 추가하려면 메뉴 2를 사용하세요. 기본값 변경 검증은 기존 파일을 지우지 않고
테스트의 임시 저장 경로를 사용하며, 정답 번호와 개수에 의존하는 풀이 테스트도 함께 검토합니다.

## 커밋 규칙·브랜치 전략

커밋은 기능·수정·리팩터링·테스트·문서처럼 하나의 검토 가능한 목적을 단위로 합니다.
메시지는 `Type: 대상과 변경 결과` 형식으로 작성합니다.
예: `Feat: 중복 없는 무작위 출제 구현`, `Fix: 저장 실패 안내 수정`,
`Refactor: 게임 책임 분리`, `Test: JSON 손상 복구 검증 추가`, `Docs: 저장 방식 한계 설명 추가`.
빈 커밋으로 수를 늘리지 않고 기존 커밋 이력을 유지합니다.

`main`은 제출 기준이고 `codex/<작업-주제>`는 기능 개발용입니다.
기능 브랜치로 미완성 변경을 구분해 검증한 뒤 `--no-ff`로 병합하며,
병합 전 작업 상태·diff·테스트·데이터 호환·사용자 파일 제외를 확인합니다.
충돌은 양쪽 변경 의도를 확인해 해결하고 영향받은 검증을 다시 실행합니다.
작은 문서·증거 보완은 main에 직접 커밋할 수 있습니다.
`codex/quiz-play`와 `codex/bonus-features`는 모두 실제 병합을 완료했습니다.
범주별 실제 커밋, 네이밍, 병합 체크리스트는 [Git 작업 규칙](docs/git-workflow.md)에 있습니다.
