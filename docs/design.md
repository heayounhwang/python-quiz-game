# 클래스와 JSON 저장 설계

## 클래스를 선택한 이유: 함수 기반 대안과 비교

이 프로그램은 같은 구조의 퀴즈를 여러 개 다룹니다. `Quiz` 객체 하나에
문제·선택지·정답·힌트를 묶고 생성자에서 검증하면, 각 기능이 잘못된 형태의 문제를
따로 검사하는 중복을 줄일 수 있습니다. `QuizGame`에는 현재 목록·최고 점수·기록을
묶어 게임 한 개의 상태와 그 상태를 변경하는 메서드를 함께 관리합니다.

| 선택 | 장점 | 단점·적합한 상황 |
|---|---|---|
| 현재 클래스 구조 | `quiz.check_answer()`처럼 데이터와 동작의 관계가 명확함. 게임마다 상태를 분리하고 임시 저장 경로로 테스트하기 쉬움 | `self`·생성자·직렬화 변환을 이해해야 함. 상태를 변경하는 메서드는 실행 순서에 영향을 받음 |
| 함수 + 딕셔너리 | 작은 프로그램에서 단순하고, 계산만 하는 순수 함수는 독립적으로 테스트하기 쉬움 | 매번 목록·점수·기록을 인자로 전달하거나 전역 상태를 관리해야 함. 검증이 여러 함수로 흩어질 수 있음 |

함수만으로도 같은 프로그램을 만들 수 있습니다. 이 프로젝트는 반복되는 문제 데이터와
게임 상태가 있고, 미션이 클래스 2개를 요구하기 때문에 클래스를 선택했습니다.
공통 입력은 객체 상태가 필요 없어 `read_number`·`read_text` 함수로 남겼습니다.
클래스 속성은 외부에서 변경할 수 있으므로 생성자 검증만으로 모든 변경을 차단하지는 않습니다.

## 클래스·입력·파일 I/O의 책임 경계

| 위치 | 주요 메서드·함수 | 책임 |
|---|---|---|
| `Quiz` / `quiz.py` | `__init__` | 문제·선택지·정답·힌트를 검증하고 속성에 저장 |
| `Quiz` | `display`, `check_answer`, `show_hint` | 한 문제 표시·정답 판정·힌트 안내 |
| `Quiz` | `to_dict`, `from_dict` | 객체와 JSON용 딕셔너리 변환. 파일은 직접 열지 않음 |
| `QuizGame` / `game.py` | `show_menu`, `run` | 메뉴 출력·분기·안전한 종료 흐름 |
| `QuizGame` | `play`, `update_best_score` | 무작위 출제·문제 수·힌트 감점·기록·최고점 갱신 |
| `QuizGame` | `add_quiz`, `delete_quiz`, `list_quizzes` | 등록·삭제·목록 조회 |
| `QuizGame` | `show_score`, `show_history` | 최고점과 회차 기록 조회 |
| `QuizGame` | `load_state`, `validate_history`, `save_state` | 디스크 I/O·저장 데이터 검증·JSON 복구 |
| `input_helpers.py` | `read_number`, `read_text` | 터미널 입력의 공백·빈 값·숫자·범위 확인. 파일 저장과 점수 계산은 하지 않음 |

숫자 입력은 `strip()` → `int()` 변환 → 범위 확인 순서입니다.
정답 판정은 `type(answer) is int`로 정확한 정수형인지 확인한 뒤 정답 번호와 비교합니다.
Python에서 `True == 1`이 참이므로 `True`가 1번 정답으로 취급되지 않게 합니다.
터미널 입력과 별개로 JSON의 숫자·목록·문자열도 검증해 외부 저장 파일의 잘못된 값을 막습니다.

## JSON을 선택한 이유와 특징

문제·선택지 목록과 점수 기록을 한 파일에 구조화하기 쉽고 사람이 내용을 읽을 수 있습니다.
표준 `json` 모듈을 사용하므로 추가 설치가 없으며, 작은 로컬 콘솔 게임을 Windows와 WSL에서
실행하기에 적합합니다. UTF-8과 `ensure_ascii=False`로 한글을 읽기 쉽게 보존합니다.

JSON의 객체·배열·문자열·숫자·불리언·null은 Python의 dict·list·str·숫자·bool·None으로
변환됩니다. `Quiz` 객체 자체나 날짜 객체를 직접 저장하는 것이 아니라 딕셔너리와
ISO 8601 날짜·시간 문자열로 변환합니다. JSON은 데이터 형식이며 프로그램 코드를 실행하지 않습니다.

CSV는 평면 표에 적합하지만 한 문제의 선택지 목록과 여러 회차 기록을 함께 표현하기 번거롭습니다.
SQLite는 동시 접근·검색·부분 갱신에 더 적합하지만 이 미션 규모에서는 스키마와 쿼리 관리가
추가됩니다. 따라서 우선 작은 단일 사용자 파일 저장을 선택했습니다.
JSON 자체에는 애플리케이션 스키마나 정답 범위 제약이 없어 코드에서 별도로 검증해야 합니다.

## 중첩 필드의 설계 근거

`quizzes` 배열의 각 객체에 `question`, `choices`, `answer`, `hint`를 묶습니다.
문제와 선택지·정답의 관계가 흩어지지 않고, 문제별 저장·불러오기가 가능합니다.
`history` 배열에는 `played_at`, `total`, `correct`, `hints_used`, `score`를 회차별로 묶습니다.
당시의 집계 결과를 기록하므로 현재 문제를 삭제해도 과거에 푼 문제 수와 점수가 유지됩니다.
다만 과거 문제 원문이나 개별 제출 답안까지 저장하는 구조는 아닙니다.

`best_score`는 과거 버전의 최고점을 보존하기 위해 독립 필드로 유지합니다.
옛 파일에 `history`가 없어도 기존 최고점을 잃지 않으며, 없는 과거 회차를 추측해 만들지 않습니다.

## 읽기·검증·대체 순서

1. 기본 문제 5개·`best_score=None`·빈 `history`를 준비합니다.
2. 기본 경로는 `game.py`와 같은 폴더의 `state.json`입니다. 테스트에서만 별도 경로를 전달합니다.
3. UTF-8로 JSON을 읽고 최상위 객체·목록·점수·개별 `Quiz`·회차 기록을 검사합니다.
4. 모두 유효할 때만 메모리의 기본 데이터를 읽은 데이터로 교체합니다.
5. 파일 없음·손상·읽기 오류는 안내하고 기본 데이터로 시작합니다. 다른 저장 파일을 자동 검색하지 않습니다.

`hint`·`history`가 없는 기존 형식은 정상 호환으로 처리합니다.
그 밖에 검증에 실패하면 일부 정상 항목만 살리는 것이 아니라 전체 기본 상태로 시작합니다.
이 상태에서 다음 저장에 성공하면 기존 손상 파일을 교체합니다.

## 저장 시점과 입력 중단 정책

| 사건 | 메모리에 반영하는 시점 | 저장·미저장 항목 |
|---|---|---|
| 퀴즈 추가 | 문제·선택지·정답·선택적 힌트 입력 완료 후 | 즉시 전체 상태 저장. 입력 중단 시 미완성 문제는 추가하지 않음 |
| 퀴즈 삭제 | 대상 선택과 삭제 확인 완료 후 | 즉시 전체 상태 저장. 취소·확인 전 중단 시 삭제하지 않음 |
| 퀴즈 풀이 완료 | 모든 문제 답변 후 | 최종 점수·완료 회차·최고점을 함께 저장 |
| 풀이 중 Ctrl+C·EOF | 진행 중인 정답 수·힌트 수는 지역 변수 | 해당 미완료 회차는 기록하지 않음. 기존 완료 기록·등록 문제·최고점은 종료 시 저장 시도 |
| 메뉴에서 Ctrl+C·EOF | 새 게임 결과 없음 | 안내 후 `finally`에서 현재 전체 상태 저장 시도 |
| 메뉴 5 종료 | 현재 상태 유지 | 전체 상태 저장 시도 후 종료 |
| 목록·점수·기록 조회 | 상태 변경 없음 | 조회 자체에서는 저장하지 않음. 이후 종료 시 저장 |

쓰기 실패 시 현재 메모리 상태는 남습니다. 사용자가 계속 진행하면 다음 저장 동작에서 다시
시도하지만 자동 재시도 루프·대체 저장 경로는 없습니다. 실패 상태에서 종료하면 변경이 유실될 수 있습니다.
파일 교체 후 손실 여부를 보장하는 복구 시스템이나 전원 장애 보장은 구현하지 않았습니다.

## 예외별 동작과 수동 복구

| 예외·상황 | 현재 동작 | 사용자 조치 |
|---|---|---|
| 숫자 변환 실패·빈 입력·범위 초과 | 안내 후 같은 입력 재시도 | 안내된 범위로 입력 |
| `FileNotFoundError` | 기본 데이터 사용 | 새 실행이면 정상. 기존 자료가 필요하면 백업 확인 |
| JSON 구문·자료형·필드·UTF-8 손상 | 안내 후 전체 기본 상태 사용 | 원본이 필요하면 실행 전 별도 복사·검토 |
| 읽기 권한·경로 오류 (`OSError`) | 안내 후 기본 상태 사용 | 접근 권한·경로·저장 위치 확인 |
| 임시 파일 생성·쓰기·교체 오류 | 실패 안내와 `False` 반환, 가능한 임시 파일 정리 | 폴더 권한·남은 용량·파일 잠금 확인 후 저장 재시도 |
| 교체 전 저장 실패 | 기존 `state.json`을 직접 덮어쓰지 않음 | 원본 유지 여부 확인. 임시 파일 정리도 실패할 수 있음 |
| `KeyboardInterrupt`·`EOFError` | 안내 후 가능한 범위에서 저장하고 종료 | 재실행 후 문제·기록 확인 |

자동 백업·`restore` 메뉴는 없습니다. 수동 백업·복구는 **게임을 종료한 뒤** WSL 프로젝트 폴더에서 합니다.
다음 명령은 사용법이며 이번 문서 보완 과정에서 사용자 파일에 실행한 명령이 아닙니다.

```bash
# 정상 데이터일 때 수동 백업. 같은 이름이 있으면 덮어쓰기 전에 확인한다.
cp -i -- state.json state.manual-backup.json

# 복구할 때 현재 파일을 별도로 보존한다.
cp -i -- state.json state.before-restore.json

# 백업의 JSON 문법을 확인한다. 필드 스키마 전체 검증은 아니다.
python3 -m json.tool state.manual-backup.json

# 자신이 저장한 정상 백업임을 확인한 뒤 복구한다.
cp -i -- state.manual-backup.json state.json
python3 main.py
```

백업의 필드와 값도 위 스키마에 맞아야 합니다. 백업 파일이 없으면 과거 사용자 데이터를
자동 복원할 수 없습니다. `defaults.py`를 수정하거나 재실행하는 것만으로 삭제한 사용자 문제가 돌아오지는 않습니다.
백업 역시 개인 데이터이므로 제출 저장소에 무심코 추가하지 않습니다.

## JSON 저장의 성능·동시성·메모리 한계

현재 방식은 데이터를 한 번에 읽고, 추가·삭제·게임 완료·종료 때 **파일 전체를 다시 씁니다**.
직렬화된 전체 크기를 S라고 할 때 읽기·파싱·직렬화·쓰기의 작업량은 대체로 S에 비례합니다.
디스크에도 임시 파일과 기존 파일이 함께 존재할 여유 공간이 필요합니다.
문제 수나 기록 수가 커지면 작은 점수 변경에도 전체 I/O가 발생해 대기 시간이 늘어납니다.
여기서 성능 수치는 측정하지 않았으며 특정 용량·속도를 보장하지 않습니다.

메모리에는 문제 객체·전체 기록이 상주하고, 로드 시 파싱된 dict/list와 새 Quiz 객체,
저장 시 JSON용 딕셔너리 목록도 잠시 함께 존재합니다. 따라서 메모리 사용은 전체 데이터 크기에
비례해 늘어나며 실제 파일 크기보다 클 수 있습니다. 기록 개수 제한·페이지 조회·스트리밍은 없습니다.
점수 기록 출력도 전체 기록을 순회하므로 회차가 많으면 출력이 길어집니다.

동시 실행을 막는 파일 잠금·버전 검사·트랜잭션은 없습니다.
두 프로세스가 같은 파일을 읽고 각각 저장하면 나중 저장이 앞선 변경을 덮어쓰는 **갱신 유실**이 생길 수 있습니다.
임시 파일 완성 후 교체는 중간에 잘린 JSON의 위험을 줄이지만 두 사용자의 변경을 합쳐 주지는 않습니다.
`fsync`와 파일 교체만으로 전원 장애·모든 파일 시스템의 내구성까지 보장하지도 않습니다.

따라서 현재는 **작은 데이터·단일 사용자·한 번에 한 프로세스**를 전제로 합니다.
문제·기록이 커지면 기록 분리·보관 정책·페이지 조회를 검토하고,
동시 사용이 필요하면 잠금 또는 트랜잭션이 있는 SQLite 등으로 전환할 수 있습니다.

힌트 감점 규칙을 바꾸면 이전 `history` 점수의 검증식과 호환 정책도 함께 바꿔야 합니다.
코드만 바꿔 예전 기록을 손상으로 오인하지 않도록 마이그레이션과 테스트를 먼저 설계합니다.
