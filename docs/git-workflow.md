# Git 커밋 규칙과 브랜치 전략

## 커밋 단위

한 커밋은 검토·설명 가능한 하나의 목적을 담습니다. 기능 추가, 버그 수정, 구조 정리,
테스트, 문서를 구분하되 같은 목적의 작은 변경은 함께 기록할 수 있습니다.
예를 들어 저장 실패 안내를 고치면서 그 오류를 재현하는 테스트를 함께 추가할 수 있습니다.
커밋 수를 늘리기 위한 빈 커밋·공백만 변경·무관한 파일 묶음은 만들지 않습니다.
기존 이력의 메시지가 나중에 정한 형식과 조금 달라도 제출 이력을 삭제하거나 재작성하지 않습니다.

## 메시지 형식과 범주

형식은 `Type: 변경 대상과 결과를 설명하는 한국어 요약`입니다.
기존 프로젝트에서 사용한 대문자 시작 형식을 유지합니다.

| Type | 기록하는 변경 | 실제 커밋·예시 |
|---|---|---|
| `Initial` | 최초 프로젝트 구성 | `57dc40d` — `Initial: 프로젝트 기본 파일 생성` |
| `Feat` | 사용 가능한 기능 추가 | `b629cee` — `Feat: 풀 문제 수 선택과 중복 없는 무작위 출제 구현` |
| `Fix` | 잘못된 동작 수정 | `43b190b` — Windows 통합 테스트 인코딩 수정과 검수 증거 기록 |
| `Refactor` | 책임·구조 정리 | `58c226e` — `Refactor: QuizGame으로 메뉴와 게임 책임 분리` |
| `Test` | 검증 사례·실행 증거 추가 | `b4188df` — 보너스 및 필수 회귀 40개와 양 환경 실행 증거 |
| `Docs` | 사용법·설계·증거 설명 | `503bbf3` — 보너스 사용법·점수 규칙·호환·검수 문서화 |
| `Merge` | 검증된 기능 브랜치 병합 | `274b209` — 보너스 5개 기능과 제출 문서 병합 |

위 표의 축약 설명은 원문 전체 메시지를 그대로 인용한 것이 아닐 수 있으며,
정확한 메시지는 `git log --oneline --all`로 확인합니다.
앞으로의 예시는 `Feat: 점수 기록 날짜 검색 추가`, `Fix: 빈 목록에서 삭제 선택 방지`,
`Docs: JSON 동시 저장 한계 설명 추가`처럼 대상과 결과가 드러나도록 작성합니다.

## 브랜치 분리 목적·이름

`main`은 제출·실행 기준입니다. 기능 개발을 별도 브랜치로 분리하면 테스트가 끝나지 않은
변경을 main과 구분하고, 문제 발생 시 영향을 추적하기 쉽습니다.
이 프로젝트는 개인 작업이므로 복잡한 장기 운영 브랜치 대신 짧은 기능 브랜치를 사용합니다.

| 브랜치 | 분리 목적 | 실제 결과 |
|---|---|---|
| `main` | 검증된 제출 코드와 문서 | 기존 최초 커밋부터 연속 이력 보존 |
| `codex/quiz-play` | 퀴즈 풀기 기능 개발 | `checkout -b`로 생성, `3bfcf5c`에서 병합 |
| `codex/bonus-features` | 보너스 기능 5개·테스트·문서 개발 | 양 환경 검증 후 `274b209`에서 병합 |

앞으로도 `codex/<작업-주제>`처럼 목적을 알 수 있는 소문자 영문 이름을 사용합니다.
작은 문서·제출 증거 정리는 기존처럼 main에 직접 커밋할 수 있습니다.
모든 과거 커밋이 기능 브랜치를 통해서만 들어온 것은 아니며, 실제 이력과 다르게 주장하지 않습니다.

## 병합 전후 체크리스트

1. `git status --short --branch`로 브랜치와 미커밋 변경을 확인합니다. 사용자 파일을 임의로 버리지 않습니다.
2. `git diff --check`와 변경 diff를 검토하고, 해당 코드 변경에 필요한 테스트를 실행합니다.
3. `state.json` 같은 사용자 데이터·임시 파일·인증 정보가 커밋 대상에 포함되지 않게 합니다.
4. 코드 변경이면 README·스키마·이전 파일 호환·테스트가 함께 맞는지 확인합니다.
5. 작업을 커밋한 뒤 `git checkout main`으로 돌아와 원격 변경 여부를 확인합니다.
6. `git merge --no-ff codex/<작업-주제>`로 병합 이력을 남깁니다.
7. 충돌이 나면 양쪽 의도를 확인해 해결하고 영향받은 검증을 다시 수행합니다. 충돌 해결을 위해 reset·force push로 기존 이력을 없애지 않습니다.
8. 원격에 push하고 로컬 HEAD와 원격 main의 해시, 작업 트리 상태를 확인합니다.

이 프로젝트의 두 기능 브랜치는 실제 `--no-ff` 병합을 사용했습니다.
검증 없이 합치거나, 문서상의 체크리스트를 과거에 실행한 증거로 대신하지 않습니다.
문서만 변경한 경우에는 코드 테스트를 무조건 반복하는 대신 링크·메서드명·실제 구현과 설명의 일치를 확인합니다.

## clone·pull 실습과 증거 대응

실제 순서는 clone → 복제본 README 수정 → commit → push → 원래 폴더에서
`git pull --ff-only origin main` → 변경 및 HEAD 일치 확인입니다.
단순히 변경 없는 pull만 실행한 실습이 아닙니다.

이미지는 직접 실행 후 캡처한 보조 증거이며, AI 평가가 이미지를 제외하더라도
코드·README·이 마크다운과 Git 이력으로 작업을 설명할 수 있도록 구성했습니다.
이미지 속 커밋 수는 촬영 시점 기준이며 이후 문서 보완 커밋이 추가될 수 있습니다.
